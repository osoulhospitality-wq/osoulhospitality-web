# Osoul Command Center — Enterprise Activation v15

هذه الحزمة هي مسار الإنتاج الخاص متعدد المستخدمين. طُبّق المخطط على مشروع Supabase وربطت به بوابة دخول مؤسسية، لكن تظل البيانات الحقيقية محكومة ببوابة الإطلاق أدناه وباعتماد نقل البيانات والاحتفاظ والاستعادة.

## القرار التقني

- Supabase: PostgreSQL + Auth + Storage + Row Level Security.
- n8n: تكامل Dragon، مسارات الاعتماد، التنبيهات، وإثبات التنفيذ.
- مزود بريد معاملاتي: يُعتمد بعد التحقق من SPF وDKIM وDMARC والتسليم.
- OCR: اختبار Google Document AI وAzure Document Intelligence على عينة 30 مستندًا عربيًا/إنجليزيًا قبل التعاقد.
- GitHub العام: كود واختبارات منزوعة الحساسية فقط؛ لا يُستخدم كسجل عملاء أو عقود.

## ما يغطيه المخطط

- عزل البيانات حسب المنشأة `organization_id`.
- أدوار Owner / Approver / Analyst / Viewer.
- فرض MFA عند مستوى قاعدة البيانات باستخدام `aal2`.
- الموردون والمنتجات والعروض وبنود العروض والعقود.
- طلبات Dragon وأحداث التنفيذ ومفاتيح idempotency.
- القرارات والاعتمادات والمستندات وسجل تدقيق يُنشأ من Triggers.
- حاوية مستندات خاصة بحد 25 MB وأنواع ملفات محددة.
- فهارس للمسارات التشغيلية الحرجة وقيود تمنع الربط بين منشأتين.

## ترتيب التفعيل

1. اعتماد مالك البيانات، تصنيف البيانات، مدة الاحتفاظ، وسياسة النسخ والاستعادة.
2. إنشاء مشروع Supabase في منطقة مناسبة بعد تقييم نقل البيانات خارج المملكة وفق نظام حماية البيانات الشخصية.
3. إبقاء `schema.sql` مصدر الحقيقة، وتنفيذ أي تعديل لاحق كـMigration مراجَعة قابلة للتدقيق.
4. إنشاء أول Organization من جلسة مستخدم صحيحة؛ ينشئ Trigger عضوية المالك.
5. تفعيل TOTP MFA وإكمال Enrollment وChallenge وUnenroll.
6. اختبار الأدوار الأربعة بجلسات `aal1` و`aal2`، وحساب غير عضو، ومستخدم موقوف.
7. ربط Command Center بواجهة خاصة؛ لا يُشحَن Service Role أو Secret Key إلى المتصفح.
8. نقل Dragon من GitHub Issues العامة إلى جداول `requests` و`request_events`، مع إبقاء GitHub للكود والأدلة العامة فقط.
9. إنشاء مسار n8n يكتب حالات accepted/processing/completed/failed وأزمنةها الفعلية.
10. تفعيل التخزين الخاص، اختبار الرفع/القراءة/الاستبدال/الحذف حسب الدور، ثم تجربة OCR.
11. تشغيل مستشاري Security وPerformance وإغلاق جميع الملاحظات الحرجة والعالية.
12. اختبار النسخ الاحتياطي والاستعادة، فقدان MFA، إلغاء جلسة، وتسرب صلاحية.
13. نشر البيئة الخاصة خلف تسجيل الدخول، ثم إيقاف نموذج الطلب العام.

## بوابة إطلاق الإنتاج

الحالة الحالية: **Conditional Go** للتهيئة الخالية من البيانات، و**No-Go للبيانات الحقيقية** حتى نجاح كل بند:

- [ ] المستودع العام لا يحتوي طلبات أو تعليقات حساسة.
- [x] MFA مفروض في الواجهة وRLS عند `aal2`.
- [ ] RLS مختبر بجلسات فعلية لجميع الأدوار والحالات السلبية بعد إنشاء حسابات الاختبار.
- [x] `anon` بلا وصول مباشر للجداول أو الدوال الخاصة.
- [x] المستندات في Bucket خاص وسياسات التخزين تتطلب العضوية و`aal2`.
- [ ] سجل التدقيق يُنشأ من قاعدة البيانات ولا يستطيع المستخدم تعديله أو حذفه.
- [ ] القياسات مبنية على `request_events` لا على تاريخ إغلاق GitHub.
- [ ] النسخة الاحتياطية والاستعادة نجحتا في اختبار موثق.
- [ ] سياسة الاحتفاظ، الخصوصية، إدارة الحوادث، وإلغاء الوصول معتمدة.
- [ ] اختبار اختراق موجه للصلاحيات (BOLA/IDOR) وفصل المنشآت نجح.

## اختبارات SQL إلزامية بعد التطبيق

- Owner يرى منشأته ويدير الأعضاء.
- Approver يعتمد العقود والقرارات دون إدارة العضويات.
- Analyst ينشئ الموردين والعروض والطلبات ولا يعتمد عقدًا.
- Viewer يقرأ فقط.
- جلسة `aal1` تُرفض رغم نجاح تسجيل الدخول.
- عضو Organization A لا يرى أو يربط سجلًا من Organization B.
- `anon` لا يقرأ أي جدول أو ينفذ دوال `private`.
- حذف المورد المرتبط أو المستند المرتبط يفشل بطريقة مضبوطة.
- الملف الذي يتجاوز 25 MB أو نوعه غير مسموح يُرفض.
- سجل Audit يبقى قابلًا للقراءة للمالك فقط وغير قابل للتعديل.

## قرار الاستخدام الحالي

- النسخة العامة v15: **Go للاختبار المنزوع الحساسية فقط**.
- مخطط Supabase والبوابة المؤسسية: **Go للتهيئة الخالية من البيانات**.
- الاستخدام التشغيلي ببيانات حقيقية: **Conditional Go** بعد إنشاء حسابات الاختبار، تفعيل TOTP، اختبار الاستعادة، واعتماد موقع معالجة البيانات.
