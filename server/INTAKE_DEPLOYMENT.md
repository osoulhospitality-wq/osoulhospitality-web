# سجل استلام الطلبات الدائم — إعداد الخادم

الحالة: مطبّق في المصدر ومختبر محليًا بمحاكاة CRM والبريد وقاعدة البيانات. ليس منشورًا أو مختبرًا ضد الخدمات الحقيقية. `completed` يعني قبول قناة واحدة على الأقل للطلب؛ لا يعني وصول البريد للمستلم أو تعيين مسؤول للمتابعة. `needs_review=true` يكشف الفشل الجزئي في السجل وسجل أخطاء الخادم.

## التهيئة قبل النشر

ينشئ مسؤول الاستضافة مجلدًا دائمًا مملوكًا لمستخدم PHP **خارج public_html وخارج مستودع الموقع** بصلاحيات `0700`. يضبط في إعداد PHP/FPM الموثوق متغير `OSOOL_INTAKE_STATE_DIR` على المسار المطلق لهذا المجلد، ويختبر قراءته من عملية الويب نفسها. لا تضع هذا الإعداد في POST أو ملف منشور. يلزم PHP 8.1+ ونظام ملفات محلي موثوق يدعم flock وatomic rename. لا تستخدم مجلدًا مؤقتًا أو network share أو أكثر من خادم يملكون مجلدات مستقلة. عدم الإعداد/الصلاحيات الخاطئة يمنع الإرسال بجميع القنوات ويظهر send-error؛ لا fallback إلى tmp.

المسار القديم `server/lead-state.php` لم يعد مستخدمًا بواسطة submit.php. قبل التبديل، أوقف استقبال الطلبات مؤقتًا أثناء نشر متناسق؛ احتفظ بسجلات claims القديمة وانقل كل معرفاتها بنفس hash اسم الملف إلى حجز في السجل الجديد بحالة review-required، أو أعد تشغيل النسخة القديمة حتى تنقضي فترة التكرار المتفق عليها. **لا تعتبر غياب السجل القديم إذنًا لإعادة إرسال طلب مجهول النتيجة.** أداة الترحيل المحلية جاهزة ومختبرة؛ لم يُنفّذ ترحيل حي هنا. تستخدم أسماء SHA نفسها، وتنشئ tombstone بحالة review-required وجميع القنوات unknown حتى إن قال السجل القديم completed، لأن القديم لا يثبت أي قناة قبلت. تحافظ على receipt السليم، ولا تستنتج نتائج تسليم أو تعيد إرسال طلب. السجلات التالفة أو timestamp-only تحجز المعرف أيضًا؛ fingerprint غير المعروف يعطي conflict بدل إعادة الإرسال.

أبقِ استقبال الطلبات متوقفًا طوال نسخ claims القديمة والترحيل وتبديل الشيفرة والإعدادات والتحقق النهائي؛ الأداة لا تقفل ملفات المصدر. بعد إيقاف استقبال الطلبات وحفظ نسخة من المجلدين، يشغّل مسؤول الخادم CLI خارج الويب:

```sh
php server/migrate-intake-claims.php --source=/private/legacy-claims --destination=/private/receipts
php server/migrate-intake-claims.php --source=/private/legacy-claims --destination=/private/receipts --apply
```

الأول dry-run بلا كتابة، والثاني يحتاج --apply صريحًا. لا تستبدل الملفات الموجودة ولا تحذف القديم، وتستخدم القفل نفسه والكتابة الذرية للمسار الجديد؛ الخروج 1 يعني أخطاء ملفات تحتاج معالجة والخروج 2 يعني إعدادًا غير صالح. راجع report الناتج وعدد الملفات planned/migrated/existing/errors قبل استئناف النموذج. يجب أن يكون مسار المصدر مستقرًا ولا يُعدّل أثناء الترحيل، والوجهة الخاصة بمستخدم الخادم؛ لا تشغّل على مجلد غير موثوق يغيّر آخرون محتواه. تحفظ الملفات القائمة كما هي حتى لو كانت تالفة وتحتاج إصلاحًا يدويًا. الحجز يحمي من التكرار لكنه لا يستعيد محتوى الطلب أو يثبت نجاح تسليمه.

## ما يخزنه السجل

لكل معرف طلب ملف JSON باسم SHA256 ومعه ملف lock. يتضمن fingerprint، receipt عشوائيًا ثابتًا (مرجع وليس كلمة مرور)، التوقيت، حالة كل قناة وعدد محاولاتها. لا يخزن أسماء أو بريدًا أو محتوى الموجز. الملفات `0600`. تحديث JSON بملف جديد وflush/fsync ثم rename؛ القفل منفصل يبقى ثابتًا. لا تحذف ملفات القفل أثناء التشغيل. حماية التطبيق لا تحمي من مسؤول نظام يغير الملفات. يجب اعتماد سياسة احتفاظ ونسخ احتياطي وصلاحيات ومراقبة امتلاء القرص؛ لا يوجد تنظيف آلي قد يعيد السماح بالتكرار.

القنوات تعمل بالترتيب CRM ← mail ← database؛ ترسل قاعدة البيانات نتيجة القناتين السابقتين. قبل كل أثر خارجي تُحفظ in_progress. إذا ماتت العملية أو رمت القناة خطأً أو كان ردها غير صالح تصبح unknown/تظل in_progress وتحتاج مصالحة. فشل HTTP الحالي يُصنف unknown لأن bool transport لا يميز رفضًا نهائيًا من timeout. قبول mail يعني قبول النقل المحلي فقط. لم يطبق fsync على المجلد الأب بعد rename؛ لذلك الاختبار يثبت تعافي توقف العملية فقط، ولا يضمن بقاء آخر rename عند انقطاع الكهرباء. فقدان قرص/خادم أو نسخ احتياطي قديم خارج ضمان هذا التنفيذ. لا يوجد ادعاء exactly-once عبر الإنترنت.

## المصالحة والتصعيد

مسؤول التشغيل يراجع `intake_outcome` الذي يحمل needs_review أو review-required، ويتحقق من معرف الطلب في قاعدة البيانات/CRM وسجلات البريد، ويسجل دليل النتيجة وقرار المسؤول. لا تعدّل السجل ولا تعيد إرسال طلب unknown آليًا. يحتفظ السجل بأثره لمنع التكرار؛ أي إصلاح قناة يحتاج إجراء إداري موثق بعد إثبات عدم قبولها. لا توجد queue أو replay أو مهمة تنبيه مجدولة مفعلة بهذا التسليم. الموجز لا يخزن محليًا، لذلك لا يمكن إعادة بناء بيانات مفقودة من hash؛ عندما تفشل جميع القنوات يحتاج المسؤول لاستعادة مصدر موثوق أو إعادة جمع البيانات من العميل ضمن إجراء واضح.

الـrate limit السابق ما زال في tmp؛ ليس سجل إثبات استلام. يشمل حاجز الإرسال claim الدائم ولا يعتمد نجاح التكرار على rate limit.

## الاختبار والرجوع

```sh
PHP_BINARY=/path/to/php python3 -m unittest discover -s server/tests -p 'test_*.py'
php -l submit.php
php -l server/intake-pipeline.php
```

الـharness للـCLI فقط، لا تستدعيه واجهة عامة، ولا يقرأ production credentials. يُقيّم source submit.php نفسه مع stubs في عملية منفصلة، ولا يتصل بالشبكة أو يرسل mail. لا يمكن اختيار adapters من نموذج HTTP. اختبارات source المحلية لا تثبت اتصالًا فعليًا أو وصولًا للبريد. يفضّل استبعاد tests من حزمة production.

قبل التفعيل: نسخة احتياطية من submit.php وإعدادات PHP والمجلد الخاص، فحص storage من مستخدم PHP، ترحيل claims القديمة، تجربة اصطناعية عبر بيئة staging مع تكاملات اختبار معتمدة. عند فشل الإعداد أعد نسخة الشيفرة السابقة بالتزامن مع سجلها المتوافق؛ لا تمسح السجل الجديد ولا تعِد تشغيل أي طلب مشتبه فيه. إغلاق القبول مؤقتًا أفضل من فقد آثار الإرسال. تحتاج واجهة operator للـledger وتنبيه فشل مجدول واختبار تعافي نسخ احتياطي قبل ادعاء متابعة مستمرة.
