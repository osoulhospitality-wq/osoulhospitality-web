# مصفوفة اختبار القبول — Dragon Intake Production v3

**حالة هذا المستند: خطة اختبار قابلة للتنفيذ، وليست نتائج فعلية.** لا تتوفر لديّ بيانات اعتماد أو اتصال بـ n8n أو Supabase أو صلاحية إرسال أحداث GitHub تجريبية حية، لذلك لم يُنفَّذ أي بند من العشرة أدناه بعد. كل بند يحدد بدقة: كيف يُنفَّذ، وما الدليل المطلوب لإثبات النجاح، بحيث يمكن لأي شخص لديه وصول لـn8n/Supabase تنفيذه ونسخ الأدلة الفعلية هنا.

## التحقق الآلي المحلي

نجح `node automation/tests/dragon-workflow.test.mjs` في التحقق من بنية الرسم، صلاحيات المرسل، مصفوفة الأحداث، توحيد مفتاح `opened/labeled`، دورة Retry، محاكاة القفل الفريد، التحذير الثابت، وعدم وجود أسرار مضمنة. هذا لا يستبدل الاختبارات الحية أدناه.

## اختبار تعافي إضافي إلزامي

- عطّل صلاحية كتابة Labels مؤقتًا بعد إنشاء القفل، وتحقق أن مسار الخطأ ينهي صف `dragon_locks` بحالة `failed` ولا يتركه `processing`.
- اجعل `Normalize Delivery` يستقبل مخرجًا فارغًا، وتحقق أن الخطأ ينتقل إلى `Post Failure` ثم `Finalize Lock: failed`.

## معايير القبول الإجمالية (يجب تحقق الكل)

- [ ] استدعاء واحد فقط للنموذج لكل `idempotency_key` عبر جميع الاختبارات.
- [ ] تعليق نهائي واحد فقط لكل دورة ناجحة.
- [ ] عدم بقاء أي صف `processing` عالق في `dragon_locks` بعد اكتمال أي اختبار.
- [ ] كل الاختبارات التسعة الأخرى (بخلاف اختبارات الأمان) تنتج صفًا واحدًا على الأقل في `dragon_events_log` يفسّر القرار.
- [ ] لا كشف لأي Credential أو مفتاح API في أي تعليق أو سجل.
- [ ] كل تعليق آلي من Dragon يحمل `execution_id` ووقت التنفيذ وتحذير "مخرج آلي أولي" الثابت.
- [ ] نجاح البنود العشرة أعلاه بأدلة فعلية موثّقة في هذا الملف (وليس بافتراض).

## كيفية تسجيل النتائج

بعد كل تنفيذ فعلي، حدّث الصف المقابل في الجدول أعلاه: غيّر "الحالة" إلى `نجح` أو `فشل`، وأضف رابط/لقطة الدليل في عمود جديد أو كملاحظة أسفل الجدول. لا تُغيَّر حالة أي بند إلى "نجح" دون دليل مرفق.
