# تثبيت مرشح استقبال دراقون واختباره

يحوّل هذا المسار طلب GitHub المأذون إلى مسودة قابلة للمراجعة. يتطلب إثبات العمل الميداني سجل أمر العمل واعتماد مسؤول المنشأة. يحتفظ ملف الاستيراد بحالة التعطيل حتى يختبره مسؤول التشغيل داخل مساحة n8n معزولة.

## تثبيت بيئة الاختبار

1. خذ نسخة استعادة محكومة من إعدادات البيئة المستهدفة والارتباطات اللازمة، وسجل إصدار n8n والإضافات. استورد الملف `automation/n8n/dragon-intake-production.workflow.json` في مساحة اختبار منفصلة.
2. أنشئ مستودع GitHub وقاعدة وبيانات اعتماد خاصة بالاختبار. في n8n، عيّن متغيرات `DRAQON_GITHUB_OWNER` و`DRAQON_GITHUB_REPOSITORY` و`DRAQON_ALLOWED_SENDER` و`DRAQON_SUPABASE_URL`. طابق قيود القاعدة مع مستودع الاختبار والمرسل المأذون.
3. اربط حقول STAGING داخل محرر n8n ببيانات GitHub محدودة النطاق، واعتماد النموذج، واعتماد HTTP من نوع Custom Auth يزود رأسي `apikey` و`x-app-api-key` بصورة محكومة. اضبط العناوين غير السرية في المتغيرات، ومفاتيح الوصول في مخزن بيانات الاعتماد المشفر. تحقق من اشتراك محفز GitHub في مستودع الاختبار وحده.
4. خصص مسؤولًا ووجهة تنبيه خاصة عندما تتوقف مهمة للمصالحة. تحقق من وصول التنبيه وسجل التتبع وتكلفة الطلب على حساب الاختبار قبل الموافقة على النقل.

## كيف يمر الطلب

يتحقق مرشح الاستقبال من المصدر والمرسل والوسم ويثبّت هوية الأمر. يُنشئ سجل قرار ويحاول حيازة قفل ذري يربط المستودع والطلب وإصدار الأمر. عندما يفقد إقرار الحيازة، يقرأ صف القفل ويتحقق من مالكه قبل المتابعة. تؤدي الملكية الملتبسة إلى توقف للمصالحة.

بعد نشر إيصال القبول، يصوغ النموذج المسودة ويختبر مدقق المخرج القيود المدعومة، ومنها الجملة الواحدة أو النقاط الثلاث عند طلبها. يحفظ المسار إيصال التسليم ثم يتطلب صفًا نهائيًا صحيحًا يعود إلى التنفيذ نفسه قبل إظهار وسم الإكمال. إذا نجحت كتابة خارجية وفُقد ردها، تحفظ آلية التوقف القفل حتى يفحص المسؤول التعليق والصف. يُستخدم فرع الإخفاق للعمليات التي يمكن التحقق من فشلها.

## قبول النسخة والتراجع

* شغّل `node --test automation/tests/dragon-workflow.test.mjs`. لكتابة سجل حالات قابل للقراءة آليًا، عيّن `DRAQON_WORKFLOW_TEST_REPORT` إلى ملف أدلة. تغطي هذه الحالات منطق العقد وبنية المسار.
* في مساحة الاختبار، أرسل طلبًا اصطناعيًا ثم حدثًا مطابقًا له. افحص أن المالك الصحيح حصل على قفل واحد، وأن الطلب يحمل إيصال قبول وتسليم واحدين، وأن حالة الصف تطابق الوسم. افحص أيضًا رفض مرسل خارج النطاق وطلب صيغة مختصرة وتعطل أحد الموصلات.
* في اختبار انقطاع الإقرار، طابق معرف التنفيذ وصف القفل والتعليق. إذا ظهر التعليق، اربطه بالمحاولة السابقة. إذا كان مصيره مجهولًا، اترك الطلب مفتوحًا للمصالحة البشرية واحفظ الأدلة. راجع حالات التوقف السابقة قبل تفعيل المعالجة مجددًا.
* عند النقل المأذون، اجعل اشتراك أحداث المستودع لنسخة واحدة فقط. راقب عدد المحاولات المعلقة وتكلفة كل مسودة مقبولة. للتراجع، عطّل المحفز الجديد، واستعد النسخة المعتمدة، وطابق الطلبات المفتوحة مع أقفالها وإيصالاتها قبل استئناف المعالجة.

## تهيئة القفل وسجل الأحداث في PostgreSQL

ملف `automation/sql/dragon_locks.sql` يُطبَّق يدويًا بصورة مستقلة عن ملفات `supabase/migrations`. يحتاج مشغّل التهيئة إلى صلاحية مالك كائنات دراقون ومخطط الإضافات في قاعدة الاختبار. قبل التنفيذ، احفظ تعريفات الكائنات والسياسات ومنح الصلاحيات القائمة في نسخة استعادة محكومة. استخرج قيمة المستودع من `DRAQON_GITHUB_OWNER/DRAQON_GITHUB_REPOSITORY` والمرسل من `DRAQON_ALLOWED_SENDER`. عيّنهما في اتصال التهيئة نفسه ثم شغّل الملف. مثال محلي اصطناعي:

```sql
SET draqon.install_repository = 'fixture-org/requests';
SET draqon.install_sender = 'fixture-sender';
```

يربط ملف التهيئة السياسات بالقيم المحددة لحظة التثبيت. يتطلب كل تثبيت أو إعادة تطبيق اختيار النطاق صراحة. أدخل بصمة مفتاح البوابة عبر إجراء إدارة الأسرار للبيئة المعنية. يعيد الملف ضبط منح جداول دراقون ودالة التحقق فقط، ويحفظ المنح الأصلية للمخطط المشترك. إذا ظهرت دالة تشخيص قديمة متاحة لأدوار الواجهة، تتوقف المعاملة قبل تطبيق أي تغيير. وثّق مالكها واعتمادياتها واتخذ قرارًا منفصلًا بتقييد الوصول إليها. افحص صلاحيات الأنظمة الأخرى قبل وبعد التطبيق. للتأكد محليًا شغّل `node --test automation/tests/dragon-provisioning.test.mjs`، ولتسجيل النتائج عيّن `DRAQON_PROVISIONING_REPORT` إلى ملف معزول.
