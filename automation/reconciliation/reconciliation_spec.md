# تسوية استقبال الطلبات وإعادة المحاولة

## الحالة والتسليم
مواصفة مُعدّة مع سياسة Python نقية واختبارات محلية. ليست مسار n8n منشورًا أو مجدولًا، ولا ترسل أي رسالة أو تتصل بخدمة. ملف reconciliation.py يمنع التشغيل الإنتاجي ويقبل معرفات TEST فقط. نجاح الاختبارات يثبت السياسة المحلية ولا يثبت تكامل HubSpot أو البريد.

## المشكلة
نجاح النموذج أمام العميل لا يثبت وصول جميع القنوات. Timeout بعد قبول الخدمة الخارجية قد يعني نجاحًا غامضًا؛ إعادة الإرسال العمياء قد تكرر جهة الاتصال أو البريد. لذلك نفصل حالات pending / delivered / failed_retryable / failed_permanent / unknown لكل قناة.

## نموذج البيانات المقترح
integration_outbox: organization_id، submission_id، channel، version، payload_ref (مرجع خاص لا نسخة مكشوفة)، state، attempts، next_attempt_at، owner_id، lease_until، provider_receipt_id، last_error_code. مفتاح فريد (organization_id, submission_id, channel, version). لا تغييرات DDL طبقت في هذه الجلسة.

## التصميم المطلوب للمحوّل الإنتاجي
1. إدخال الطلب الصحيح وoutbox في معاملة واحدة. الرد للعميل يقر الاستلام الداخلي، ولا يدعي نجاح كل قناة.
2. عامل مجدول يعتمد صراحة؛ يلتقط صفوفًا مستحقة بعقدة قفل ذرية مع مدة lease ويحررها عند الانتهاء. لا يكفي قرار Python وحده لمنع التنافس.
3. إنشاء CRM عبر upsert موثق ومعرف مصدر فريد. مفتاح منع التكرار يعاد استخدامه عند المحاولة. إذا لم تدعم القناة idempotency فافحص receipt/lookup قبل إعادة الإرسال.
4. نجاح مثبت برقم مزود → delivered. خطأ 429 أو 5xx معروف قبل القبول → failed_retryable؛ احترام Retry-After مع jitter؛ 4 محاولات كحد أولي مقترح. أخطاء 401/403 أو بيانات غير صالحة → تصعيد وإيقاف القناة، لا تكرار بلا نهاية.
5. انقطاع بعد إرسال الطلب أو غياب جواب حاسم → unknown ثم reconcile_provider. لا يعاد الإرسال تلقائيًا حتى دليل أنه لم ينفذ أو قرار مخول.
6. لا تعاد قناة ناجحة أثناء إصلاح قناة أخرى. سجل audit مختصر لا يتضمن أسرارًا. غياب owner_id يحجز الطلب في قائمة مراجعة.
7. نوافذ إعادة المحاولة في السياسة المحلية: 60، 300، 1800، 7200 ثانية بعد المحاولة. الخدمة الإنتاجية تضيف jitter وتحترم الحد الأقصى المعتمد وRetry-After.
8. الإنذار الداخلي له مستلم وقناة مصرح بهما. لا تنشئ إنذارًا يرسل لعميل. إن فشل الإنذار نفسه يظهر في لوحة الأخطاء ويستخدم مسار بديل معتمد.

## عقد API الإنتاجي المقترح
POST /internal/outbox/claim يلتقط الصفوف بعقدة ذرية؛ لا يستخدم GET لتغيير الحالة. الطلب يحمل هوية خدمة مصادقًا عليها وscope محدودًا وlease. نتيجة claim لا تحتوي إلا الصفوف المصرح بها. POST /internal/outbox/{id}/complete يتطلب lease_token ومعرف المزود. POST /internal/outbox/{id}/fail يتطلب رمز خطأ مصنفًا لا نصًا شخصيًا. جميع الواجهات خاصة ولا تقبل secret في query string. هذه أسماء تصميم، لم تنشأ endpoints فعليًا.

## خطوات تفعيل n8n لاحقًا
الحصول على SDK reference الحقيقي وعقد node الرسمي، ثم إعداد مسار جديد غير نشط في مشروع أصول المحدد، validate ثم pinned tests، مراجعة الأذونات والمستلمين، ربط outbox staging، تجربة E2E غير مراسلة، ثم اختبار إرسال داخلي مصرح، ثم نشر بعد اعتماد البيئة. لا تستبدل Dragon الحالي بصمت. حفظ نسخة وتاريخ تغيير ومعرف تراجع قبل أي تعديل.

## دليل القبول
طلب مكرر لا ينشئ contact/task مكررين؛ رفض CRM يبقي الطلب محفوظًا؛ فقد الاستجابة لا يكرر الإرسال؛ غياب مسؤول ظاهر؛ فشل قناة لا يعيد قناة ناجحة؛ تجاوز retry cap يرفع incident؛ تعطل العامل أثناء التنفيذ يعاد تسويته بعد انتهاء lease دون تكرار؛ بيانات عميل آخر غير قابلة للالتقاط. تجربة التنافس والـ crash تتطلب datastore حقيقيًا وتبقى غير مختبرة هنا.
